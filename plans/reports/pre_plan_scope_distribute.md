# Hook Materialization Scope Plan

## Context

EVCrate already builds one verified, immutable projection per harness and one shared advisor-controller closure. Publication is currently HOME-only: `createPublicationPlan` consumes `homePolicy.bindings`, publication state and recovery are rooted at `$HOME/.evcrate/publication`, and `--project-root` supplies invocation context but does not select a publication destination. Several generated hook registrations or wrappers also conflate the installed hook root with the active workspace.

The approved contract is a hybrid two-root model. `<home>/.evcrate/**` always remains HOME-owned and participates exactly once; `--target` filters only harness projections; `--scope home|project` selects the harness destination and defaults to `home`; project publication writes the selected harness’s `outputRoots`, `additionalRoots`, and `projectDocs` beneath the active project. One neutral verified projection feeds both scopes. Registration chooses the installed wrapper, wrappers locate child resources from their own file location, and every `*_PROJECT_DIR` plus child `cwd` continues to identify the active workspace.

## Approach

Keep build adapters scope-neutral and perform scope-specific path binding only in publication. The neutral projection uses project-relative/native registration forms. HOME materialization parses the known registration/config documents and rewrites only validated command fields to absolute paths beneath the selected HOME binding; project materialization copies the neutral registration unchanged. Arbitrary replacement across hook bodies is prohibited.

Preserve the existing single HOME transaction for `--scope home`. For `--scope project`, commit a controller-only HOME transaction first, then a project harness transaction from the same verified build snapshot. Hold the HOME publication lock through both phases and acquire the project lock second, so another publisher cannot introduce controller/projection version skew. A project-phase failure never rolls back the already committed shared phase and returns a structured partial result.

Generalize the journal engine around an explicit destination root and transaction workspace. HOME workspaces remain under `$HOME/.evcrate/publication` on the HOME volume. Project journal/marker/lock state lives at `<context.stateRoot>/project-publication/<projectIdentity>/`, while its temporary stage/backups use the fixed direct-project child `.evcrate-publish-<releaseId>` so rename promotion remains on the project volume. The journal records and validates both roots and the canonical project identity; successful project publication removes the temporary workspace and does not retain project-local backups.

## Critical files & anchors

- `src/protocol/publication-payloads.ts` — scope request contract, phase results, project identity, deterministic binding validation.
- `src/distribution/publication-plan.ts` — shared/controller planning and HOME-versus-project harness bindings.
- `src/distribution/publication-rules.ts` — structured registration/config materialization without hook-body rewriting.
- `src/distribution/publication.ts` — HOME atomic transaction, ordered project phases, locking, partial outcomes, and state migration.
- `src/distribution/publication-recovery.ts` — scope-bound journal validation and same-volume recovery workspaces.

## Implementation plan

### 1. Freeze the CLI and wire protocol contract

1. In `src/cli/arguments.ts`, add `PublicationScope = 'home' | 'project'`, parse a scalar `--scope`, reject every other value, and expose `scope: 'home'` when omitted. Permit it on `publish`, `recover`, and the publication-bearing compatibility commands `distribute publish|all|recover`; reject it for unrelated commands instead of silently ignoring it.
2. Keep `--home` and `--project-root` semantically independent. `--home` always selects shared infrastructure. `--project-root` selects only project-scoped harness output and continues to default to invocation `cwd`; `--scope home` never redirects through it. Do not emulate project mode by setting `--home` to a project.
3. Extend `PublishRequestPayload` with required `scope`. Extend `RecoverRequestPayload` with required `scope` and `projectIdentity`, requiring `null` for HOME and the canonical SHA-256 identity for project recovery. Add `projectIdentity: string | null` to publication/recovery results with the same invariant.
4. Replace the flat dry-run/apply publication result with two ordered logical phase records: `shared` (destination scope `home`, controller binding only) and `harness` (destination scope equal to the request). Each record carries its own binding order and changes; apply records also carry phase status, release ID, and retained release ID. In HOME mode both logical phases share the one transaction/release ID. In project mode they have independent release IDs. Recovery returns only the explicitly requested state domain, with its phase, release ID, binding order, and recovery action.
5. Add a resource-control `partial` result variant containing the validated publication payload plus serialized `PUBLICATION_FAILED`/`ROLLBACK_FAILED` error. It exits with publication category code 5. Emit it only after the shared project phase committed and the harness phase failed; shared-phase failures remain ordinary errors and the harness phase is marked `not-started`.
6. Update `src/protocol/resource-payloads.ts`, `src/protocol/resource-control.ts`, `src/cli/dispatch.ts`, `src/cli/compatibility-distribution.ts`, `src/distribution/local-build.ts`, `src/cli/types.ts`, exports, and integration command builders so scope and recovery identity are forwarded end to end. Correlation checks must validate each phase against its destination policy rather than assuming every change is a HOME binding.

### 2. Derive scope-specific bindings without changing adapter ownership

1. Extend `SelectedTargetContext` in `src/context/invocation-context.ts` with normalized project binding descriptors derived from each manifest’s `outputRoots` (the loader’s normalized `output_root` plus `additional_roots`) and `projectDocs`; retain the existing normalized `homeBindings`. Represent directory roots and root-level project documents distinctly so publication does not fake project documents as directories.
2. For project publication, call `projectIdentity(context.projectRoot)` and require an existing, real, non-symlink, owner-controlled project root before planning or mutation. Keep lexical `resolveProjectRoot` for general invocation context; enforce mutation-grade checks only at the publication boundary.
3. Keep `ProjectionBuildContext` unchanged: no scope, HOME, publication, lock, controller, or transaction fields. The build still resolves and verifies exactly one current schema-2 build snapshot before either publication phase.
4. Expand the manifest HOME publication-rule enum and target manifests for explicit registration rewrites: Codex, Claude, Gemini, Antigravity, and Copilot. OMP’s path-prefix rule and Claude’s HOME skill-root exclusion remain HOME-only. Project mode uses manifest local roots/documents directly and never applies HOME layout rules.
5. Define deterministic phase order from the selected manifest order and each manifest’s declared binding order. Shared is always `.evcrate/bin`. HOME harness order preserves the current promotion order, including `.gemini` before `.gemini/config`; project harness order uses each target’s output/additional roots followed by its project documents. Reject duplicate or overlapping destinations before inventory reads.

### 3. Make every generated hook closure scope-neutral

1. **Claude:** retain project-relative commands in canonical `.evcrate/source/.claude/settings.json`. Add a structured HOME settings rewrite that parses JSON and rewrites only `statusLine.command` and `hooks.*[].hooks[].command` entries whose executable path is the validated `.claude` neutral prefix.
2. **Codex (`src/adapters/codex/hooks.ts`):** change context and pre-tool wrappers to resolve their child hook with `path.join(__dirname, <child basename>)`, validate the child as a regular non-symlink file, and use `CODEX_PROJECT_DIR || process.cwd()` solely as workspace/cwd. Keep `.codex/hooks.json` and `.codex/config.toml` neutral; update the HOME rule to parse hook JSON command fields and validate/rewrite only the generated TOML `command` assignment for `run-mcp-package.sh`, never arbitrary file text.
3. **Gemini (`src/adapters/gemini/runtime.ts`):** make bridge children `__dirname`-relative, preserve the active workspace for `GEMINI_PROJECT_DIR`, `CLAUDE_PROJECT_DIR`, and spawn `cwd`, and keep generated `.gemini/settings.json` project-relative. Add a structured HOME settings rewrite for native hook command fields.
4. **Antigravity (`src/adapters/antigravity.ts`):** remove `rewriteGlobalHooks` from adapter generation so `.antigravity/hooks.json` is neutral. Keep wrapper-to-`.original.cjs` resolution self-relative; use the payload/env-derived project root for `cwd`, `CLAUDE_PROJECT_DIR`, `GEMINI_PROJECT_DIR`, and `AGY_PROJECT_DIR`. Add a structured HOME rewrite that maps validated `.antigravity/hooks` registrations to the actual `.gemini/config/hooks` binding.
5. **Copilot (`src/adapters/copilot/hooks.ts`, `bridge.ts`):** emit project-neutral hook/status-line commands rooted at `COPILOT_PROJECT_DIR || process.cwd()`. HOME publication rewrites only the validated commands in `hooks/evcrate.json` and `evcrate/managed-settings.json`. Keep child scripts `__dirname`-relative and derive `EVCRATE_GLOBAL_CONFIG_ROOT` from the installed bridge location rather than `COPILOT_HOME`, while leaving `COPILOT_PROJECT_DIR` and child `cwd` equal to the active workspace.
6. **OMP (`src/adapters/omp/templates.ts`):** retain self-relative hook resolution and derive the config root from the generated runtime module/resource root, not `os.homedir()`, so the same module works at `.omp/evcrate` in a project and `.omp/agent/evcrate` in HOME.
7. **Pi (`.evcrate/targets/pi/files/agent/extensions/evcrate/index.js`, `paths.js`):** derive the installed agent/resource root from the loaded extension location for EVCrate-owned files. Preserve `PI_CODING_AGENT_DIR` normalization only for third-party package discovery. This prevents project-loaded extensions from falling back to `$HOME/.pi/agent` while retaining active workspace data from Pi hook context.
8. Regenerate all seven projections/build manifests through the existing generator after source changes. Assert no generated registration contains a HOME-only path and no wrapper searches ancestor projects to locate an installed child hook.

### 4. Build shared and harness plans from one verified snapshot

1. Refactor `createPublicationPlan` into a verified-build resolver plus phase planners. Resolve `resolveCurrentBuild` once; pass the immutable result to both phases and include the same build-manifest digest in every phase result/journal.
2. The shared planner always emits one whole-directory controller operation from `.evcrate/source/.evcrate/bin` to `<home>/.evcrate/bin`, independent of selected targets and requested harness scope.
3. The HOME harness planner maps `homePolicy.bindings`, applies only declared HOME rules, and retains existing structured JSON merge behavior for Pi/Copilot.
4. The project harness planner maps output/additional roots to `<project>/<root>` and project documents to `<project>/<document>`. Apply the same managed-file inventory, stale-file deletion, shared-JSON merge, hash, mode, and CAS policies without HOME transforms.
5. Preserve ownership records for unselected targets when `--target` updates only a subset. Reconcile stale files only inside touched target bindings; never forget or delete another target’s managed set.
6. Make every change path phase-relative and validate it against exactly one phase binding. Unmanaged file/directory collisions, binding overlap, symlink ancestors, type changes, and out-of-root paths produce conflict/path failures before promotion.

### 5. Generalize apply, locking, state, and recovery

1. Introduce a transaction descriptor consumed by apply/recovery: logical phase, publication scope, destination root, durable state root, transaction workspace root, selected targets/bindings, optional project identity, and retention policy. Reuse the existing stage/backup/promote/CAS implementation rather than adding a second project publisher.
2. Before either project-scope mutation, finish both phase plans and preflight project identity, destination ancestry, collisions, workspace containment, and usable destination volumes. Retain `$HOME/.evcrate/publication/publish.lock` as the first lock for every apply. HOME scope executes controller plus harness under the current single ordered transaction. Project scope commits the controller-only transaction, keeps the HOME lock to prevent controller version skew, acquires `<stateRoot>/project-publication/<identity>/publish.lock`, then applies the project harness transaction; every path acquires locks in that order, so no reverse-order deadlock is possible.
3. Store project journal, marker, and lock at `<stateRoot>/project-publication/<identity>/` with owner-only permissions. Store stage/backups at `<project>/.evcrate-publish-<releaseId>` with owner-only permissions and a name derived exactly from the journal release ID. Validate the canonical destination root, project identity, fixed workspace name, device, inode, ownership, and containment on every recovery step.
4. Write and fsync a staged project journal before creating its workspace. Recovery may safely remove a journal whose workspace is absent only when status is `staged` and every operation is unpromoted. After workspace creation, keep the existing write-journal → promoting marker → per-operation snapshot/backup/rename → fsync → committed marker ordering across both filesystems.
5. Never retain a completed project transaction beneath the project. Remove its workspace after a durable global commit marker; keep `retainedReleaseId: null`. HOME retains the existing bounded one-release backup policy.
6. Version publication state to schema 2. The HOME marker tracks shared-controller and HOME-harness records separately while a HOME-scope journal can update both atomically; a project controller-only transaction updates only the shared record and preserves HOME harness ownership. Shared-only journals use an empty selected-target set and exactly the `.evcrate/bin` binding instead of attributing the controller to a harness. The project marker binds the harness record to `projectIdentity` and canonical `projectRoot`.
7. Under the HOME lock, recover any valid schema-1 journal with the existing schema-1 rules before schema-2 work. Migrate a completed/recovered schema-1 marker by splitting `.evcrate/bin` metadata into the shared record and existing target bindings/managed paths into the HOME harness record; atomically write schema 2, then remove obsolete retained schema-1 transaction data. Invalid or ambiguous legacy state fails closed.
8. Make `recover --scope home` recover only the HOME journal (whether it represents the combined HOME transaction or a controller-only shared transaction). Make `recover --scope project` require/derive the matching canonical project identity and recover only that identity-keyed project harness journal; it must not search or mutate HOME state. Return the requested state domain and phase action unambiguously.
9. On a project harness error after shared commit, attempt only project rollback. Return top-level `partial` with `shared=committed` and `harness=failed` plus the sanitized phase error; if rollback itself fails, preserve the journal and report `ROLLBACK_FAILED`. Never compensate or downgrade the committed shared controller.

## Verification

- **CLI/protocol:** default `home`; exact `home|project`; scope forwarded through direct, request-file, and compatibility publication; structured partial result exits 5.
- **Destination matrix:** all seven harnesses materialize to manifest HOME bindings and separately to project-local roots/docs; advisor/bin appears only at the selected HOME.
- **Runtime semantics:** registrations resolve the installed wrapper; wrappers resolve children from self-location; child cwd and `CLAUDE_PROJECT_DIR`/`CODEX_PROJECT_DIR`/`GEMINI_PROJECT_DIR`/`AGY_PROJECT_DIR`/`COPILOT_PROJECT_DIR`/OMP/Pi equivalents identify the active workspace.
- **Transactions:** HOME remains one atomic ordered publication; project is shared-HOME then project-harness, with explicit partial completion and phase-specific recovery.
- **Safety:** unmanaged collisions, path escape, symlink ancestors, owner mismatch, CAS drift, project identity mismatch, substituted workspaces, and invalid legacy state fail closed.
- **Distribution:** archive inventory still contains one neutral projection per harness and one controller closure; installation/publication does not mutate the verified snapshot.

## Assumptions & contingencies

- `--scope home` is the compatibility default; changing that default requires a separate protocol/CLI decision.
- Shared `<home>/.evcrate/**` always runs and is never filtered by `--target`; a fully standalone project controller is not part of this change.
- Project publication requires an existing owner-controlled project directory. If HOME/state/project are on different devices, only each individual phase is atomic; the documented partial result is the contract between phases.
- Neutral project-relative registration is the source form. If a vendor’s config schema cannot represent the expected environment expression, its adapter emits a deterministic project-root loader command and HOME materialization rewrites that validated command field; it does not introduce a second projection tree.
- `--home` selects publication output; external harnesses must be launched with that same HOME/config-home when vendor discovery depends on process HOME. Publication does not silently reconfigure vendor launchers.
- External harness discovery remains vendor-owned. Deterministic tests must exercise every generated registration/runtime closure; live vendor qualification remains a separate operator gate and cannot weaken the release checks above. Current release verification is Linux-only, so this change must not claim Windows runtime qualification.
